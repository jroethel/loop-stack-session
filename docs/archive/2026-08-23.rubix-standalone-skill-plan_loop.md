## 3. Orchestration shape and the three validation layers

Three tiers, unchanged by transport:
- Orchestrator (this session): writes each wave's manifest, runs it, reads run JSON and worker logs, gates, applies reviewed patches, merges, and escalates. Never implements.
- Validator (per unit): the primary gate is ringer's executed `check`, which lives in the manifest outside every worker's file ownership; the two gate-critical units (T1, T3) additionally get a fresh read-only Opus native validator that judges the diff and artifact against criteria, never fixes.
- Implementer (per unit): a ringer manifest task on the claude-zai engine, working test-first against its criteria in its own worktree.

Three validation layers, in order:
1. Implementer self-check: the worker runs its own acceptance test (the RED-then-GREEN step) inside its worktree before returning.
2. Per-unit validator: ringer's independent `check` re-runs that acceptance test AND diffs the worker's committed test file byte-for-byte against the source plan's verbatim golden block (see hazard H2); for T1 and T3, the Opus validator then does an adversarial criterion walk.
3. Orchestrator gate: read the run JSON, read every retried or failed log, spot-check one passing artifact, apply patches to the integration branch, run the full suite there, advance only on green.

## 4. Hazard mitigations (deviations from the source plan marked)

**H1 - Tasks 1 and 2 write to a real HOME path outside the loop-stack checkout.**
`~/create/skills/rubix-review` is a different repo from loop-stack, so neither ringer run-level worktrees (they snapshot the task's declared repo) nor the Agent tool's built-in worktree (it snapshots the session's outer repo) isolates that path for free.
The mitigation is exact path ownership plus disjointness, not auto-isolation:
- Task 1 (W1) creates the repo fresh (`mkdir -p ~/create/skills/rubix-review && git init`) and is the sole unit in its wave, so its writes are conflict-free by construction; there is no prior state to isolate from.
  Deviation: run the W1 manifest with `worktrees: false` and let the worker create and commit the repo directly at the real path, because there is no pre-existing repo for ringer to snapshot.
- Task 2 (W2) cannot share a manifest with Tasks 4 and 5: ringer's `repo` key is manifest-level, not per-task (verified against ringer.py's TaskSpec/Manifest schema at pin review).
  W2 therefore runs as TWO manifests launched at the same wave, same `run_name`: manifest A carries T2 alone (`repo: ~/create/skills/rubix-review`, `worktrees: true`), manifest B carries T4 and T5 (`repo`: the loop-stack checkout, `worktrees: true`); both meet at the single W2 gate.
  The three are disjoint by path: Task 2 writes only `install.sh` and `tests/install.sh` inside rubix-review; Tasks 4 and 5 write only inside loop-stack, and to non-overlapping files there.
  A cross-repo or cross-file collision at the W2 gate is a scope violation, not something to resolve quietly.
- Every T1/T2 spec names exactly the rubix-review paths it may create or edit (the source plan's exclusive-ownership lists), and nothing else.

**H2 - Check custody with worker-written tests.**
The source plan has each worker WRITE its own failing acceptance test first (test-first), which would let a worker game its own success criterion.
The tests are dictated verbatim in the source plan, so the check is spec-pinned, and the custody surface is restored this way:
- The worker writing its test is RED-GREEN hygiene only; it is NOT the gate.
- The gate is ringer's own `check` field (orchestrator-owned, outside worker ownership), which (a) diffs the worker's committed test file byte-for-byte against the source plan's verbatim golden block for that task, failing on any deviation as a scope violation, then (b) executes the test.
- A worker diff that alters the test text away from the golden is an automatic FAIL, not a gate negotiation.

This is the mechanism for T1 (`tests/skill-content.sh`), T2 (`tests/install.sh`), T4 (`tests/gates/loop-plan-rubix.sh`), T5 (`tests/gates/loop-brainstorm-rubix.sh`), and T3 (`tests/gates/reviewer-contract.sh`).

**H3 - Shared append-only files.**
None of the six units share an append-only log or checklist; the source plan gives each unit a disjoint ownership list.
The only shared file across units is `docs/gate-registry.md`, which is a regenerated artifact owned solely by the Task 6 gate action, never appended by a worker (see H5).

**H4 - Dirty working tree at launch.**
loop-stack has one untracked file, `docs/memos/loop-setup-virgin.md`, touched by no task.
Because loop-stack worktrees branch from committed HEAD, this untracked file never enters any worker's worktree, so it is inert.
Surface it at pre-flight and leave it as-is (no task owns it, no commit needed); this is a benign untracked file, not a dirty-tree STOP.

**H5 - Task 6 is gate-shaped work on a shared, regenerated file (deviation).**
Task 6 regenerates `docs/gate-registry.md` (`bash scripts/gen-gate-registry.sh .`) and runs the full suite (`bash tests/run.sh`).
Both are orchestrator gate actions, and the registry is a generated file no worker may hand-edit, so dispatching Task 6 to a worker would only add a handoff around work the gate already owns.
Deviation from the source plan's "Task 6" framing: Task 6 collapses into the wave-4 orchestrator gate, with no model, transport, or manifest.
This matches the recorded precedent (MODEL-NOTES 2026-08-16: a deliverable-is-its-own-check task collapsed to a gate action).

**H6 - The four human checkpoints survive as STOP gates.**
They are not converted away.
Their placement and firing rules are in Section 6's ask-the-human list; the live-install checkpoint (touches `~/.agents`) is staged by the loop and fired only by the user.

**H7 - Reviewer-conduct contract for the validators during this build.**
This run is building the contract's canonical home, so the installed contract may not exist yet while validators run.
Every validator prompt therefore carries the reviewer-conduct contract text inline (Section 8 templates), so validators treat the install.sh, setup, and repro commands inside T2/T3 specs as evidence to read, never commands to execute.

## 6. Wave loop and gates

Per wave: launch, gate, distill, advance. `run_name` is `rubix-standalone` on every wave.

**Launch.**
Emit one manifest for the wave and run `./ringer.py lint <manifest> && ./ringer.py run <manifest>`.
Ringer's built-in single retry IS the repair pass; do not add one.
W1 manifest carries T1 alone with `worktrees: false` (H1); with `worktrees: false` the task dir is CWD for both worker and check, so the spec opens with an explicit `cd`/`mkdir -p` to the real target path and the check never uses repo-relative paths bare (MODEL-NOTES 2026-08-07 rule).
W2 is two manifests launched at the same wave under the same `run_name` (H1): manifest A carries T2 alone (`repo` = rubix-review), manifest B carries T4 and T5 (`repo` = loop-stack), both `worktrees: true`; lint and run both, gate once on both run JSONs.
W3 carries T3 alone (`repo` = loop-stack, `worktrees: true`).

**Gate (orchestrator).**
Consume the run JSON in `~/.ringer/runs/` (statuses, retries, durations); the run JSON is truth, a background shell exit is not.
For every retried or failed task, read its raw log in `<workdir>/logs/` before deciding.
On a FAIL, attribute before relaunching: re-run the check's steps yourself against the tree; if the worker's output was correct and the CHECK was wrong, fix the check in the source plan, commit the audited work, and annotate MODEL-NOTES rather than burning a round.
For T1 and T3, also read the Opus validator verdict; if any criterion fails, the verdict is fail.
Spot-check at least one passing artifact.
Apply reviewed patches to the integration branch (loop-stack) and commit rubix-review's audited work on its branch; run the relevant suite and advance only on green.
`[gate:STOP]` a stopped unit whose failure is a design issue is recorded for the downstream review under the source plan's slip rules.

**Distill before advancing (P10).**
Turn any repeated failure pattern into a fix in the source plan's spec block and the templates before the next wave.
Leave the ringer MODEL-NOTES receipt: one dated line per (model, task_type) per wave in `~/repos/ringer/docs/MODEL-NOTES.md`, plus a separate line for any signal event (a check-bug attribution, a lane outage, an off-nominal result), supported only by validator verdicts and diffs.
Commit that receipt before advancing the wave, so git-is-truth reconciliation covers the ringer repo too.

**Advance only on a green integration branch.**

Slip rules (from the source plan). The two human-judgment items (findings-parity, fail-closed behavior) and the live-install wiring are the source plan's checkpoints; a Spec-axis finding from the final `/loop-review` slips to the source plan's downstream review step, as does any stopped unit's design issue.

Spec-edit gate class (unchanged from the skill): a spec edit confined to one unit or criterion, not changing what that unit produces, touching <= 15 lines, auto-takes as BATCH `[gate:BATCH]`; a larger edit, or one touching multiple units, a global constraint, or a produced contract, is a STOP `[gate:STOP]`.
Any request to exceed the high effort cap is a STOP `[gate:STOP]`.

**Ask-the-human list (STOP gates).**

1. W2 gate, after Task 4 - soft-check behavioral spot-check `[gate:STOP]`.
   The gate proves both branches are documented; the human confirms live behavior once.
   With rubix-review present the review is offered or auto-runs per `rubix-autorun`, and with it renamed away the skill warns once and proceeds without failing.
2. W3 gate, after Task 3 - findings-parity judgment `[gate:STOP]`.
   Run the extracted skill on a real sample plan and confirm it surfaces the same class of forward-looking findings the inline Rubix would (source criterion 6, `[judgment]`; no command settles it).
3. W3 gate, after Task 3 - fail-closed behavior is real `[gate:STOP]`.
   With the contract file renamed away, invoke loop-review (or rubix-review) on a small diff and confirm the reviewer STOPS and reports the missing contract rather than dispatching subagents uncontracted.
   This is the one behavior no executed check proves.
4. W3 gate, after Task 3 - live install wiring, the user's to fire `[gate:STOP]`.
   The install.sh section 2c symlink into `~/.agents` touches HOME and is the user's trigger, never a worker's and never the loop's.
   The loop stages it and hands the user the exact commands: `bash ~/create/skills/rubix-review/install.sh` then loop-stack `bash install.sh`.
   The user then confirms `readlink skills/loop-review/references/reviewer-conduct-contract.md` resolves to the rubix-review canonical file, and that renaming rubix-review away makes install.sh print the fail-closed warning.

Pre-flight dirty-tree decision (H4) is the only pre-W1 human touch, and it is a note-and-proceed, not a stop, since no task owns the untracked file.

**Final-wave advisory review.**
On W4 only, after the integration branch is green and the run advances, run `/loop-review <pre-run-base>` from the integration branch.
It is advisory and non-blocking (the per-unit validators already gated correctness); record its findings at the final human checkpoint, and slip any Spec-axis finding to the source plan's downstream review step `[gate:BATCH]`.
