# I52 Board Bases Spike - Findings

Spike for Task 1 of the Obsidian Board MVP plan (docs/plans/2026-09-02.I52.obsidian-board-mvp-plan.md).
Question settled: does native Obsidian Bases render 8 kanban columns with distinguishable colors, or is a CSS snippet needed?
Host: Jeremy's Mac, Obsidian 1.13.7, Bases core plugin, Cortex vault.
Method: 16 fake card notes across all 8 columns in a scratch folder inside the vault, the two committed `.base` templates copied in, observed live through the Obsidian CLI (`base:views`, `base:query`, `eval` DOM geometry).
The human visual glance (brief criterion 8) is DEFERRED and is marked unverified-by-human below.

## What native Bases did

Grouping works.
`groupBy: {property: column}` grouped the cards into all 8 columns, confirmed by the rendered group headings: `backlog`, `next-up`, `in-session`, `blocked-on-you`, `blocked-on-fact`, `awaiting-review`, `handed-off`, `done`.
The global filter `board_card == true` selected exactly the fake cards and nothing else in the vault.
`base:views` reported the view as `By lane  cards`, so the finalized `.base` schema parses under 1.13.7.

Layout falls short of kanban.
Native Bases renders the cards view with a JS-virtualized layout: each group is `position: absolute` with an inline JS-computed `top` and `inset-inline: 0` (full width), so the groups stack vertically down the page rather than sitting side by side.
Measured natively: the 8 groups share the same left edge (570) with increasing tops (180, 568, 956, ...), each spanning the full container width (915px), and container `scrollWidth == clientWidth == 915` (no horizontal extent).

No native color.
Bases core exposes no per-value hook on a card: a card element carries only the class `bases-cards-item` plus an inline `width/height` style, with no `data-*` attribute for any property value.
All cards computed the same background (`rgb(15,15,15)`), so nothing distinguishes a staleness band.
Frontmatter `cssclasses` does NOT propagate to a Bases card: after adding `cssclasses: [board-band-N]` to every note, zero card elements carried a `board-band-*` class.
CSS cannot select an element by the text of a property value, so a static snippet cannot color a card by its `staleness` band through Bases core.

## The exact `.base` shape that worked

`assets/board/by-lane.base`:

```
filters:
  and:
    - 'board_card == true'
views:
  - type: cards
    name: By lane
    groupBy:
      property: column
      direction: ASC
    order:
      - column
      - repo
      - staleness
      - health
      - title
      - last_work
      - position
```

`assets/board/by-repo.base`:

```
filters:
  and:
    - 'board_card == true'
views:
  - type: table
    name: By repo
    order:
      - repo
      - column
      - title
      - staleness
      - last_work
      - health
```

Deviation from the plan's starting point: the plan wrote `groupBy: column` as a scalar and a bare top-level `order` list.
Obsidian 1.13.7 Bases takes `groupBy` as an object (`property` plus `direction`) and `order` as a per-view key, so both were finalized to that form.
The view name `By lane` is load-bearing for the CSS scope (see below), so Task 4 must keep it verbatim.

## Validated frontmatter key names

Every key in the plan's card-note frontmatter contract read correctly in Bases and is safe for Task 4 to emit:
`board_card`, `repo`, `source`, `column`, `token`, `staleness`, `last_work`, `position`, `behind`, `health`, `render_asof`, `title`.
The two views reference `column`, `repo`, `staleness`, `health`, `title`, `last_work`, `position`; all resolved.

## CSS-needed: yes

Native Bases stacks the 8 groups vertically and colors nothing, so a snippet is required for the kanban shape.
`assets/board/loop-board.css` was authored and verified live.
It pulls each group out of Bases' absolute positioning (`position: static !important`, clearing the inline `top`/`inset-inline`/`height`) and lays the container out as a two-row column-flow grid (`grid-auto-flow: column`, `grid-auto-columns: 260px`), which pairs each heading directly above its lane because heading and group are alternating siblings in `.bases-cards-container`.
After the snippet: the 8 lanes sit side by side (measured lefts 842, 1114, ... at 260px each), share a common top (180), each heading sits directly above its lane (heading top 138, group top 180, same left), and `scrollWidth` grew to 2436 against a 915 client width (real horizontal extent).
The snippet is scoped by `data-view-name="By lane"`, the only per-view hook Bases exposes, so no other Bases view in the vault is affected.
Ceiling recorded in the CSS: forcing `position: static` disables Bases' card virtualization, so all cards render at once, which is fine at a board of dozens of cards.

Staleness color is deliberately NOT in the CSS, because Bases core gives no per-card value hook.
Recommendation for Task 4: bake a per-band colored emoji into each card's `title` (band 1 green, 2 yellow, 3 orange, 4 red, matching the plan's staleness bands), which renders as text inside the card and needs no CSS.
This is the robust, plugin-free way to satisfy the "distinguishable colors" half of the glance test.

## Glance verdict

Programmatic geometry verdict (from live DOM measurement): PASS on the kanban shape.
With the two `.base` templates plus `loop-board.css`, all 8 columns render as distinguishable side-by-side lanes with a column heading atop each, and "what needs me" is legible lane-first (`blocked-on-you`, `awaiting-review`, `next-up`) without opening a repo.
The staleness-color half is satisfied by the Task 4 emoji-in-title recommendation, not by CSS.

Human visual glance: DEFERRED, unverified-by-human.
Screenshot capture was unavailable on this host (the installed Obsidian build reports out-of-date CLI support and `dev:screenshot` / CDP `Page.captureScreenshot` returned no image), so the verdict rests on DOM geometry rather than a rendered picture.
