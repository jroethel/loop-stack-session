## Outcome

An observability framework over Jeremy's work: one kanban board per host makes the state of every project under the repos root visible - where it paused, what's queued, what's blocked, what's stranded locally, and which projects haven't had a visit in a while.
Conforming repos contribute full cards; a non-conforming repo contributes a degraded card derived from git alone (last commit, uncommitted, ahead of remote), so the board covers all 24 repos on this host, not just the 2 currently conforming.
Each project's work items appear as cards in workflow columns, so the column a card sits in is the record of where things stand.
At the repo level, a session (or Jeremy) asked to resume reads recorded state and names the true frontier instead of reconstructing it from file mtimes and diffing handoffs against reality.
Resuming well is what the visibility enables; it is not an execution feature of the board.
Why the board exists in the larger workflow: reduce manual effort and attention per project, so Jeremy's time elevates to orchestration, ideation, brainstorming, and verification, with the reclaimed attention going to longer-running work and durable meta assets.

Presupposition verdict: #52 named a per-repo pointer file as the fix.
The real outcome is the observability board; the pointer survives as the per-repo recording layer the board reads.
The "Where I left off" heuristic in `config/conventions.md` (newest handoff vs newest commit) is demoted to documented fallback, not superseded: it remains the degradation path when recorded state is missing or older than HEAD, because a crashed session degrades to git, never to nothing.

## End artifact

The host kanban itself, rendering all repos under the root.
First proof of value: on the host holding a local checkout of sys-prompts-cc, the board resolves its ambiguity (names its authoritative handoff, shows the older one consumed and archived); if no such checkout exists where the board first runs, the proof repo is chosen from the repos present there.
From day one the board flags every repo holding unpushed or uncommitted stopping points - the ones that most need pickup and are invisible to GitHub/GitLab today.

## Done looks like

- One command on the host renders the board: all repos under the root, each repo's cards in loop-stack workflow columns, with colors, last-work date, local-vs-remote position, and what's queued next.
- The board pivots: grouped by repo, or by workflow lane across all repos (every resume-ready card in one lane). Both are renders of the same cards with no new state.
- Any card renders a paste-ready resume prompt, serialized from its recorded and derived state; generating it writes nothing. What executes that prompt is out of scope here and recorded on #45.
- The render touches no network for git signals: uncommitted and ahead-of-remote come from local state; "behind remote" is shown as-of-last-fetch with its timestamp, never presented as current.
- Cards derive from three sources - GitHub tracker, GitLab tracker, local repo state - and one card can join references across two or all three; card identity rides the existing doc filename token grammar (`.I52.`-style tokens), which already exists to keep a doc and its tracker item joined.
- Freshness is honest by construction: derived facts are computed at render time; recorded facts carry an as-of stamp and render visibly differently from derived ones, with staleness of the recorded half surfaced on the card. The board never claims recorded facts are current.
- Per-source health renders on the board: a source that failed (auth lapse, timeout, rate limit) shows as failed for the repos it covers, never as zero cards or a silent omission.
- In any conforming repo, sessions record state incrementally during work, not only at handoff time, because the handoff skill is human-invoke-only and a quota-killed session never reaches it; the recording is bounded to one session card per session, updated in place.
- The session card is created when the session starts and patched as work proceeds, closing with a terminal status; a card with a start and no close is therefore, by construction, a session that died mid-work, and the board renders it as such without anyone recording anything at the moment of death.
- The board self-reports skipped recording: a repo whose recorded state is older than its newest commit renders a derived went-stale flag, so a session that recorded nothing is visible without anyone remembering to check.
- A take-stock refresh rebuilds a repo's recorded state on demand from git, handoffs, and the tracker.
- Marking a handoff consumed requires a per-action disposition (each next action executed or explicitly superseded); archival then happens automatically and is verbose-announced under archive rule 5. `docs/handoffs/` holds only live handoffs.
- The handoff lifecycle is an append-only transition log (action, disposition, when), and "current state" is always derived from that log, never held in a mutable status field; "was this action already done" is answered from history, not trusted from a flag. (MLflow deprecated its mutable stage field for exactly this reason.)
- A new `lifecycle-lint` class enforces the handoff lifecycle for handoffs created after the adoption date only (an `-since` gate, mirroring `filename-grammar-since:`); the 18 pre-adoption handoffs in this repo are grandfathered, with a one-time bulk backfill offered under human confirmation, never forced through the done-gate.
- The view is read-only and always derived; state changes flow through sessions and `tracker.sh`. The recording convention, by contrast, does write: it creates session cards, marks consumption, and archives handoffs in every conforming repo, always verbose-announced.

## Approach

Chosen: local recording convention + host-derived read-only board.
Each conforming repo records its own state as a side effect of working, and a host-level board derives cards from the three sources at render time.
Observability is layered: judgment facts are recorded once where they happen, everything derivable is computed fresh, and the view holds no state of its own.

Load-bearing bounds set at Rubix time:

- The recording tax is capped: one session card per session, updated in place; take-stock derivation is the path for anything derivable, so hand-recording covers only facts derivation genuinely cannot reach.
- Card identity is pinned to the existing filename token grammar rather than left open, because seam 1 ships session cards and a token-incompatible identity would force a seam-1 rewrite at seam 3.
- Rollout is piloted: the convention rolls to 1-2 repos first, validates against the proof-of-value case, then propagates via the template-version mechanism.
- The recording convention is a standalone deliverable: a session in a single conforming repo must be able to answer "where did I leave off" with no host board built, so the original #52 ask ships even if the board slips.

Alternatives considered at decision time:

- Derive everything, no recording layer - nothing to maintain, but consumed-vs-live, phase, and effort-shape are exactly the non-derivable judgment facts; observability degrades to inference. Survives as the take-stock refresh engine.
- Hosted board as the home (GitHub Projects v2 or a forked kanban app) - zero render work, but blind to unpushed/uncommitted stopping points, which are the highest-value signals; also account-split and hosting burdens. Parked as a possible future view layer only.

## Success criteria

1. `[executed-check]` One host command renders the board; every repo under the repos root appears - conforming repos with full cards, non-conforming repos with a degraded git-derived card.
2. `[executed-check]` A repo with uncommitted changes or unpushed commits is flagged, computed with no network access; verifiable by making a scratch change and re-rendering.
3. `[executed-check]` A tracker-sourced card reflects tracker state at render time; change a label, re-render, the card moves column.
4. `[executed-check]` At least one card joins a tracker issue and a local artifact and renders as a single card.
5. `[executed-check]` Negative join: two similarly numbered or named items from different repos or sources render as distinct cards, never merged.
6. `[executed-check]` Marking a handoff consumed without per-action dispositions is rejected; dispositions append to the transition log rather than mutating a status field; with dispositions, archival fires automatically and is announced; the new lint class exits non-zero on a consumed-unarchived handoff and ignores handoffs dated before adoption.
7. `[executed-check]` Standalone resume: in a pilot repo with no board rendered, the recorded state names the authoritative handoff and the next step.
8. `[executed-check]` Per-source health: with one source's auth broken or its call failing, that source renders as failed on the board rather than as zero cards.
9. `[executed-check]` Skipped-recording flag: a repo with commits newer than its recorded state renders the went-stale marker, and a session card opened but never closed renders a died-mid-work marker.
10. `[executed-check]` Proof-of-value acceptance: on the host holding its local checkout, sys-prompts-cc's recorded state names the authoritative handoff and the older one is consumed and archived.
11. `[executed-check]` A chosen card emits a paste-ready resume prompt derived only from recorded and derived state, and generating it changes nothing (`git status` identical before and after); the lane pivot renders the same card set as the repo grouping, verifiable by matching card counts.
12. `[judgment]` A glance at the board answers "where did each project leave off, what needs me" without opening any repo. (Reformulation attempted; criteria 1-11 cover the mechanics, the glance-quality call stays human.)

## Seams (blast-radius order)

1. Per-repo recording convention - session cards (opened at session start, patched in place, closed with a terminal status), handoff consumption as an append-only transition log with per-action dispositions + announced archiving, take-stock refresh, lint class with `-since` gate and grandfathering, legacy backfill offer. Session cards are harness-agnostic: no field assumes Claude Code, so any harness (pi, opencode, just) can write and read them. Standalone deliverable; everything else reads it.
2. Host-level repo discovery - repos root configuration, conformance test, exclusion rules, degraded cards for non-conforming repos.
3. Card derivation - the three sources, joins via the token grammar, per-source health.
4. Board render - columns, colors, last-work date, local-vs-remote position, freshness stamps, grouping by project or pivoted by lane across projects, per-card resume-prompt output.
5. Propagation - pilot on 1-2 repos, then template-version bump, "Where I left off" demoted to fallback, roll to conforming repos.

## Survey amendment (2026-08-31)

A five-artifact survey (MLflow, Langfuse, vibe-kanban, claude-code-kanban, cyanluna.skills + Nimbalyst article) contributed two mechanisms, folded into seam 1 and criteria 6 and 9 above:

- Handoff lifecycle as an append-only transition log with derived current state (MLflow's deprecated mutable stage field is the precedent against the alternative).
- Session cards opened at session start and closed with a terminal status, so an unclosed card is structurally a died-mid-work session (Langfuse start/patch lifecycle plus MLflow terminal-status semantics; MLflow's orphaned-RUNNING gap is why the staleness flags stay layered on top).

The survey's remaining findings were validation or planning-level techniques (multi-window staleness signals, sentinel attention markers, tail-read caching, vibe-kanban's git panel field list) and live in the session record, not the brief.
