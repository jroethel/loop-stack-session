## The decision to be made

What surface displays the board, and what artifact does the board emit to reach it.

The genuine architectural fork is **not** TUI versus HTML versus served page.
It is: **does the board emit files that existing applications already know how to read, or does it own a process and a UI of its own?**
Every file-emitting option is a consumer of the same derivation and several can coexist; every process-owning option is a commitment.

## Candidate surfaces

Seven, grouped by the fork above. Verification status is marked per candidate and is not uniform.

### File-emitting (no process owned, several can coexist)

**A. Generated markdown mirror in-repo, e.g. `BOARD.md`.**
The repo's own native pattern and the one candidate the first pass never considered at all.
`scripts/gen-mirrors.sh` already renders tracker state into `ISSUES.md`, `BACKLOG.md`, and `WAYFINDER.md`, each carrying a `generated:` / `source of truth:` / `regenerate:` / `DO NOT EDIT` header and each gitignored.
Verified: that pattern exists and is in use; `ISSUES.md` currently shows issue #52 at the top.
Strengths: zero new technology, readable in a terminal, in an editor, on GitHub, and inside Obsidian; costs nothing to keep alongside any other option.
Weaknesses: colors are absent, 8 columns render poorly in markdown tables, and the pivot means emitting the card set twice.
Open: does a markdown board actually satisfy the glance criterion, or is it a fallback view only.

**B. Obsidian vault as the control surface.**
The candidate Jeremy pointed at, and the reframing that produced it: vaultwise's relevance is not that it runs FastAPI, it is that it already writes markdown into an Obsidian vault, so **the vault is the surface and Obsidian is the app**.
Two shapes worth separating: a single generated kanban-format markdown file, or one note per card with frontmatter plus a live query view.
Strengths, if the facts below hold: a real kanban application with drag-and-drop, columns and colors handled by the app rather than by loop-stack, sync across hosts and to mobile, and drag-to-move that writes back into a file a script can read - which is the parked write-back feature arriving nearly free.
Weaknesses: the board becomes reachable only where the vault syncs; a generated file inside a synced vault invites conflict handling; and it puts a GUI app between Jeremy and a bash-derived artifact.
**Verification status: UNVERIFIED, and this is the largest gap in this brief.**
Confirmed on RIT-UADV2223: there is no Cortex vault at the path vaultwise's example config names, no `~/.config/vaultwise/`, no Obsidian application, and no `.obsidian` directory anywhere under `$HOME` or `/mnt/c/Users`.
The vault lives on another host; vaultwise's own example config references `/Users/jjrdar` paths and `../exp-know-capture` specs, pointing at the macOS host.
A resuming session must verify on the host that holds the vault: the vault path and v5 structure, whether a kanban community plugin is installed and what file format it expects, whether Obsidian Bases or Dataview is available for a query-driven view, and how the vault syncs between hosts.
Nothing about Obsidian's plugin file formats in this brief should be treated as established; the first pass made claims from memory and they were not checked.

**C. Static self-contained HTML file.**
The option the discarded plan chose unilaterally, which is the reason this brief exists; it gets no credit for having been written up already.
Verified: nothing external is required; the repo's own generated-artifact conventions cover it; ringer ships static dashboards the same way (`~/repos/ringer/dashboard/dashboard.html`, `~/repos/ringer/dashboard/ringside.html`).
Strengths: zero dependencies, keeps loop-stack a bash repo, real colors and layout, a CSS-only pivot needs no JavaScript, and the file is servable later by anything without a code change.
Weaknesses: no auto-refresh, one command per look, and it is a fifth artifact type in a stack that already has markdown mirrors.

### Process-owning or host-application options

**D. herdr plugin.**
Verified in depth on this host; herdr 0.8.2, installed at `~/.local/bin/herdr`, server and client sockets live in `~/.config/herdr`.

What herdr's "kanban" actually is, since the parent brief named it as a view-layer candidate: it is the **agent panel**, not a kanban.
Jeremy's `config.toml` carries `agent_panel_sort = "priority"`, and release notes describe `ui.status_indicators = "symbols"` giving distinct shapes for `blocked`, `working`, `done`, `idle`, and `unknown`.
Those are lifecycle states of live agent processes bound to panes; herdr's own skill file states a name "is cleared when that agent exits, is released, or is replaced".
The full API schema (`herdr api schema --json`, 251,527 bytes, protocol 19) was enumerated: 108 methods across workspace, tab, pane, agent, worktree, layout, notification, popup, and plugin.
**There is no card, board, item, task, or kanban entity anywhere in it.**
Conclusion: 22 of the 24 repos have no running agent and structurally cannot appear in the agent panel, so the agent panel cannot host this board.

What herdr can do is host a plugin, and this is the cleanest extension seam of any candidate.
A plugin is a directory holding `herdr-plugin.toml` plus executables, linked with `herdr plugin link <path>`; no fork and no patch of herdr.
From herdr's published plugin documentation: "A plugin can be a Bash script, JavaScript app, Lua script, Rust binary, or any other argv command your machine can run."
`[[panes]]` is a first-class manifest section, and herdr's own canonical example is a project board:

```toml
[[panes]]
id = "board"
title = "Project board"
placement = "overlay"
command = ["herdr-board"]
```

Placements are `overlay`, `popup`, `split`, `tab`, `zoomed`; pane content is whatever the command writes to stdout.
`[[events]]` hooks fire on herdr events such as `worktree.created`, and `[[link_handlers]]` match a regex against a clicked URL and invoke an action, which would make a card's issue URL actionable.
`[[actions]]` receive a rich context object including `workspace_cwd`, `focused_pane_cwd`, `focused_pane_agent`, `focused_pane_status`, and `selected_text`.
Strengths: bash is first-class so nothing changes about loop-stack; the board lands where Jeremy already works all day; event hooks and link handlers come free; a single manifest can carry both a TUI pane and an action that opens a file-based board.
Weaknesses: terminal rendering only unless a plugin can reach `pane.graphics.set`, which was not verified; and herdr's own skill refuses to operate unless `HERDR_ENV=1`, so a herdr-hosted board is reachable only from inside herdr.
Verification status: API surface, method list, absence of card entities, agent lifecycle semantics, and config keys all verified locally. The manifest format is from herdr's published docs and was not tested. No plugin is installed here, so nothing was built or run.

**E. ringer ringside tab.**
Verified by reading source.
`ringer hud` starts a persistent Ringside page; the server is stdlib `ThreadingHTTPServer`; there is a derived SQLite read model (`ringer db`) and a configurable `hud_port`.
The blocking finding: tabs are added by a Python function that string-injects HTML into `ringside.html` - `inject_models_tab_into_ringside_html()` at `~/repos/ringer/ringer.py:5065`, called from `read_ringside_html()` at `~/repos/ringer/ringer.py:5387`.
A board tab therefore means writing a second `inject_*` function inside `ringer.py` and wiring it into that reader, so loop-stack's core observability feature would live in ringer's repo, in a single file whose subparsers sit past line 11,000.
Strengths: a genuinely persistent served page, an existing read model, and runs plus projects on one surface.
Weaknesses: every board change becomes a two-repo change, and it couples loop-stack to ringer's Python.

**F. vaultwise FastAPI route.**
Verified by reading source, and **the first pass's dismissal of this was wrong on the reasoning**, though the technical facts hold.
Stack: FastAPI, uvicorn, jinja2, python-multipart, markdown-it-py, uv-managed; launched as `vaultwise web --port 8701` bound to 127.0.0.1.
Routes are decorators inside a 481-line `create_app()`, and there is a real router seam: `app.include_router(admin_module.create_admin_router(...))` at `~/repos/vaultwise/src/vaultwise/web/app.py:478`.
So a `/board` route is a new `APIRouter` plus a template, added with roughly one line.
The first pass rejected this as "the board squats in an Obsidian content pipeline", which was a domain-purity argument, not a requirements argument, and it also obscured candidate B by treating vaultwise as a web host rather than as a vault writer.
A resuming session should score it against the rubric instead: it provides a served page with auto-refresh, on a service already running, at the cost of loop-stack depending on uv plus FastAPI.

**G. Standalone served page owned by loop-stack.**
Not researched, listed for completeness so the option set is honest.
Would mean loop-stack running its own long-lived process, and would revive the access-control finding (Lens B finding 7 in the parent brief) that was declined only because no served page had been chosen.

## The cross-cutting fact that makes this reversible

Nothing in this section exists yet; it is a design finding from the discarded planning pass, kept because it is what makes the view-technology decision low-stakes.

If the derivation stage emits flat records and the render stage is a pure filter from those records to an output, then **every surface above is a consumer rather than a coupling**.
Candidates A, B, and C become three renderers over one derivation and can all coexist; D can host any of them or draw its own; E and F become consumers living in another repo.
The decision then does not need to be right the first time, and a second surface costs one filter.

The record shape that was designed is reproduced here so this brief stands alone.
It is offered as a starting point and is itself one of the open decisions listed below, not a settled interface.
Tab-separated, one record per line, no header row, no quoting, no field containing a tab.

Discovery records, one per repo found under the repos root, all fields from local git with no network call:

```
REPO  name  abspath  conforming  last_commit_iso  uncommitted  ahead  behind  fetch_asof_iso
```

`conforming` is 1 when `config/repo-state.md` exists at the repo root.
`ahead` and `behind` come from `git rev-list --left-right --count '@{u}...HEAD'`, whose left side is the upstream, and are both the literal `-` when there is no upstream.
`fetch_asof_iso` is the mtime of `.git/FETCH_HEAD`, present so `behind` can be rendered as-of-last-fetch instead of as a current fact.

Card records, plus a health record per source consulted, plus the discovery records passed through unchanged so a renderer can draw per-repo chrome:

```
CARD    repo  tokens  column  kind  asof  staleness  flags  ref  title  location  note
SOURCE  repo  source  status  detail
```

`tokens` carries `I52`-style tracker tokens and is the cross-source join key.
`kind` is `recorded` or `derived`, which is what lets a surface render a claim about the past differently from a fact computed at render time; `asof` is populated only for `recorded`.
`flags` is a comma-separated subset of `went-stale`, `died-mid-work`, `uncommitted`, `ahead`, `no-upstream`, `abandoned`.
`note` carries the session card's recorded next step verbatim, and is the single non-derivable judgment fact on a card; without it a resume prompt can only restate what the board already displays.
`SOURCE` records are emitted on success as well as failure, so a source that failed renders as failed rather than as a repo with no work.

For cost calibration on the render layer specifically: the discarded plan's static-HTML renderer plus its test came to roughly 165 lines of bash, which is the order of magnitude any single surface should be expected to cost.

   If it weighs at all, Obsidian's drag-to-edit-a-file changes the ranking materially.
5. Is a herdr-hosted board acceptable given it is reachable only inside herdr (`HERDR_ENV=1`)?
6. Should more than one surface ship, given they are all consumers of the same TSV?
7. Does a long-lived process anywhere in this stack cost enough to rule out E, F, and G on principle?
