# Rubix Review as a Standalone Skill - Idea Brief

## Outcome

The Rubix review - the forward-looking two-lens judgment of a *proposed* artifact - is trapped inline in loop-plan Step 6.
It can only run on plans, at one point in the workflow, and other sessions have to read it out of loop-plan by hand to reuse it.
Restated as outcome: the Rubix review is a standalone, artifact-agnostic capability any session or skill can invoke on any proposed artifact, and it becomes the single canonical home for the reviewer-conduct contract that three skills currently duplicate.

Presupposition verdict: the proposed action (own SKILL.md, model rubric, loop-stack depends via an install check) holds.
The coupling analysis this session confirmed the review consumes only an artifact, an optional spec, and model engines - nothing loop-stack-specific - so the extraction is sound.
The one correction the analysis forced: loop-review's by-role model rule, not Rubix's inline hard pins, is the portable pattern to carry over.

## End artifact

This is meta-tooling, so the test is the first real deliverable it unblocks, not the tool itself.
First real consumer: loop-plan Step 6 invoking the extracted skill instead of running the review inline, plus the first ad-hoc "Rubix this artifact" run on a real artifact outside the plan flow.
It ships when loop-plan calls the skill and the triplicated conduct contract collapses to one source.

## Done looks like

- A user or a skill can invoke the Rubix review on any artifact and get the two-lens findings-with-severity output, with no loop-plan or loop-stack context required.
- loop-plan Step 6 calls the skill via soft-check: present means offered, or auto-run only when the config default is on (off by default); absent means a one-time warning per context, then fallback - never a hard failure, never a per-plan nag.
- loop-brainstorm offers a Rubix pass on the finished brief before it goes to planning.
- loop-review and loop-drive read the reviewer-conduct contract from the one canonical source, with zero verbatim duplicate copies left.
- Ad-hoc usage: invoke the skill by its own trigger ("use the rubix review" on an artifact you name), from any session where the standalone skill is installed - it depends on nothing loop-stack-specific, so it also works in a bare repo.

## Approach

Chosen: extract the two-lens forward review as a standalone, artifact-agnostic skill in its own repo, vendored into loop-stack by install.sh.
Un-pin the models to a by-role plus cross-model-diversity rubric; make the skill the canonical home of the reviewer-conduct contract that loop-review and loop-drive then source; wire it as a soft-checked call at loop-plan Step 6, at loop-brainstorm on the finished brief, and as a first-class ad-hoc entry point.

Alternatives considered:

1. Shared review primitive with lens-packs - extract the common substrate so Rubix and loop-review become thin callers of one core.
   Rejected: it forces loop-review's backward-looking diff-axes and Rubix's forward-looking lenses into one object though they are different jobs, and it refactors a working skill nobody asked to change - over-factoring.
2. Plan-only relocate - lift Rubix out but keep it scoped to reviewing plans.
   Rejected: it throws away the "invoked at different points, read by other sessions" reuse that motivated the request.
3. Extract but leave the conduct contract triplicated.
   Rejected by the user: the identical-prose triplication is textbook DRY, and the extraction is its natural moment to collapse.

Rationale at decision time: the coupling analysis showed the review consumes only artifact plus optional spec plus engines, so artifact-agnostic extraction is the honest scope; the lenses genuinely differ from loop-review, so they stay separate skills; the conduct contract is identical text in three files, so it collapses to one source.

Own repo, not an in-repo loop-stack skill: this decision was reopened by a Lens A review arguing that every named call site lives inside loop-stack, so an outside repo buys version drift for portability no consumer yet cashes in, and an in-repo skill with the same no-loop-stack-dependency boundary would defer that drift with zero rework.
Overruled deliberately: the review has outgrown "use rubix from loop-stack" and needs its own place - a standalone identity is the point, not a cost to defer.
The drift surface that buys is accepted and tracked as an open question below.

## Success criteria

- The extracted skill runs the two-lens review on an artifact with no spec present and produces findings-with-severity for each lens. `[executed-check]`
- The extracted skill runs in a target repo with zero loop-stack conventions and returns the review, not a missing-dependency error. `[executed-check]`
- loop-plan Step 6 invokes the skill by soft-check: present is offered (auto-run only when the config default is on, which is off by default), absent warns once per context and falls back; both paths observable. `[executed-check]`
- The reviewer-conduct contract resolves to exactly one canonical definition; a grep of the contract text across skills returns one source plus references, zero verbatim duplicates. `[executed-check]`
- The model rubric hard-pins no model name in the lens-engine position and states a cross-model-diversity recommendation. `[executed-check]`
- On a sample plan, the extracted skill surfaces the same class of forward-looking findings the current inline Rubix would. `[judgment]`

The last criterion kept its judgment tag: the reformulation toward "same class of findings" still rests on taste about finding quality, which no command settles.

## Seams

Independently checkable pieces, in blast-radius order:

1. The extracted skill itself - SKILL.md, references, model rubric, conduct contract.
   Everything else depends on this existing; checkable by invoking it standalone.
2. The canonical conduct contract plus loop-review and loop-drive re-sourcing it.
   Depends on the skill existing; checkable by grep for duplicate contract text.
3. loop-plan Step 6 rewrite from inline block to soft-checked call.
   Depends on the skill existing; checkable by running loop-plan with the skill present and absent.
4. loop-brainstorm brief-review call site.
   Depends on the skill existing, independent of the loop-plan seam.
5. Vendoring via install.sh plus the config auto-run default.
   Integration glue, checkable by running install and inspecting the config toggle.

## Known vs guessed

- Verified this session: the review consumes only artifact plus optional spec plus engines (coupling table, read from the three SKILL.md files); the conduct contract is verbatim-triplicated across loop-plan, loop-review, loop-drive (grep); loop-review already un-pins models and advertises zero-setup in the target repo (read).
- Believed-unchecked: install.sh can vendor an external repo's skill as cleanly as it symlinks the in-repo ones - not verified against install.sh internals.
  If wrong, the vendoring seam needs a different mechanism.
- Guessed: config or chain-state has, or can cheaply gain, a per-skill auto-run default slot.
  If wrong, the "don't confirm every time" behavior needs a new config location.

## Seed backlog for the new rubix-review repo

These are not loop-stack items and must not graduate into loop-stack's tracker.
They seed the new repo's own backlog once it exists, both raised by the Lens A review of this brief.

- Variable lens count.
  Restart context: the extraction ships the current two lenses (A + B); make the count a knob - sometimes one lens is enough, sometimes a third is wanted - as the new repo's first enhancement.
- Raw-idea entry point.
  Restart context: a Rubix pass earlier than any drafted artifact, at the raw-idea moment, to catch issues before even a brief is written.

## Out of scope

- Merging Rubix's lenses with loop-review's Spec and Standards axes - they stay separate skills.
- Changing loop-review's or loop-drive's review logic - only their contract-sourcing changes.
- Any new model-intel or routing infrastructure - the rubric consumes existing routing conventions if present, and falls back to the session default otherwise.
- Lens-count flexibility and a raw-idea entry point - deferred to the new repo's own backlog (see Seed backlog above), not this extraction.

## Open questions for planning

- The exact mechanism by which loop-review and loop-drive source the canonical contract (read from the vendored file vs a shipped shared reference), preserving loop-review's zero-setup-in-target-repo promise.
- Confirm the repo and skill name; the user is calling it `rubix-review`, used as the working name here.
- Where the config auto-run default lives (chain-state.md vs a skill-level config) and its key shape.
- Whether the optional third high-stakes lens stays in the extracted skill or becomes a rubric recommendation.
- How install.sh vendors the external repo (submodule, copy, or symlink) and how version drift between the standalone repo and the vendored copy is managed.
