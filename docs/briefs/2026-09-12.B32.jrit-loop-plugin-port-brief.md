## Approach

Chosen: a fresh product repo in the mattpocock/plugin shape - plugin and marketplace manifests, 11 self-contained prose skills (shared references single-copied inside their owning skills, cross-skill dependencies converted to skill invocations), one sanctioned receipt helper as the only shipped executable, repo-side CI holding the structural gains, full stranger scope now (LICENSE, versioning, stranger-first README, npx route), and tests as the engine-neutral structure checks plus `claude plugin validate --strict` plus a small eval set.

Considered: in-place restructure of loop-stack-session (the prep doc's recommendation - keeps history and remote, but mixes session history into the product tree forever); the superseded brief's two-repo split with loop-stack-session as ongoing dev home (perpetuates the heavy session repo as the active home, exactly the scaffolding being retired); a fully script-free port (rejected by the 2026-09-12 trust audit - it silently deletes the one non-forgeable gate in the system).
Rationale at decision time: the fresh repo gets the template shape by construction rather than by filtering, and the jrit umbrella is the stated destination.

### The receipt helper (the sanctioned executable exception)

The per-script trust audit found that every script already routes its writes through tracker.sh, whose enforcement concentrates in four verbs an agent cannot be trusted to replicate:

- `done --ran CMD`: re-executes the cited check itself, captures the real exit code, posts the receipt including a failure, and routes a non-zero result to `agent:review` instead of done.
- `claim`: receipt-comment-before-label-flip ordering plus race arithmetic over all receipts, failing on a lost race.
- `status`: the atomic remove-all-then-add-one swap guaranteeing exactly one active `agent:` state.
- `next-eligible`: the stale-claim wall-clock sweep and line-anchored blocked-by resolution against a consistent snapshot.

These four ship as one small helper (~180 lines, gh/glab only) inside the plugin; everything else tracker.sh does (create, comment, close, label, mode) is passthrough the skills do directly.
Named losses from retiring the rest of the script layer, accepted: the `agent:done` label block was always cooperative at the boundary (raw gh could bypass it), so the helper preserves the real property - the sanctioned path is non-forgeable when used, and loop-review audits receipts.
The dirty-tree preflight survives as one exact command in prose whose any-output result means stop.

### Tracker model

The repo's own issue tracker is the state store.
loop-setup writes one pointer doc declaring the mode (github, gitlab, or prose-managed local markdown) and the conventions; skills run gh/glab directly per that doc, and the four enforcement verbs run through the receipt helper.
The `agent:` label family survives as the single status schema; evidence-gated done stays mechanical via the helper; next-eligible stays a helper verb.
Wayfinder's tracker-native model (one labeled map issue, child tickets, native blocking relations) is the template for everything; mirrors die because the tracker's own UI is the view.
Local mode's settled minimal shape: a single issues markdown file, one section per issue carrying number, title, state, and labels as field lines, `agent:` states included; the receipt helper does not cover local mode, so claim/done enforcement is absent there - acceptable because local mode is single-machine (the exact field grammar is planning detail).
Known gap carried, not hidden: concurrent-session ownership handoff beyond claim/race/stale (#45) stays open and out of scope.

### Stub pattern (optional external tools)

Probe, use, degrade, disclose - owned by the consuming skill as one prose block: a one-line probe, what presence unlocks, the native fallback, and a one-line disclosure when the fallback is taken.
No central registry, no config keys, no install-time wiring; one shared wording template paragraph lives in the portability-doctrine reference so the five consumers stay aligned.
Applications: ringer (loop-drive probes a known path with env override; present offers ringer transport, absent compiles waves onto background agents), herdr (loop-drive probes `HERDR_ENV`; inside herdr it may dispatch workers into panes via `herdr api`, with compatibility as a probe-time check, never a pinned version), rubix-review (the standalone sister repo; present skills offer it, absent they call out plainly that the optional Rubix review is unavailable and continue), and the future board.

### Portability doctrine

Prose and the tracker are the source of truth; harness features are adapters and accelerators; nothing behavioral lives only in a manifest, a frontmatter field, or harness memory.
Concretely: the repo tree stays skills-first (bare SKILL.md directories npx-discoverable), so plugin.json is a thin adapter and other engines' packagings can be added in parallel; every skill reference is relative to its own directory, so `${CLAUDE_PLUGIN_ROOT}` appears in no skill body; structure checks stay engine-neutral bash, with `claude plugin validate` as the CC-only extra lint; eval cases are authored as engine-neutral fixtures run through the CC runner today and replayable via ringer against other engines; loop-drive's prose is layered into a portable core (waves, routing chain, gate classes, receipts) plus a per-harness execution appendix, with the tracker as the coordination bus so any tool that runs bash can pick up the baton; frontmatter context fields are optimization hints whose behavior is also stated in prose; the per-repo managed section targets AGENTS.md as canonical with CLAUDE.md as pointer, pending one verification; the handoff skill remains the canonical portable resume mechanism, with auto-memory as the CC accelerator.
The autonomy knob's repo default lives as one key in the pointer doc; a session may override it in conversation; loop-auto.sh and chain-state mechanics die.
