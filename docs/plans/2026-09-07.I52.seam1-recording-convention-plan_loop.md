## 3. Orchestration shape and the three validation layers

Three tiers, transport-independent:

- Orchestrator (this session, on Jeremy's Mac, in `/Users/jjrdar/create/loops/loop-stack-session` on branch `i52-seam1-recording-convention`): runs the wave loop, the gates, the patch applications, the four orchestrator-lane tasks, spec edits, and escalation; reads logs, verdicts, and core diffs only; never implements a dispatched unit.
- Validator (a fresh `opus` subagent per dispatched unit): adversarial re-check of the worker's claim against the actual artifacts (the applied diff, the executed check output, the produced files); reruns the acceptance suite independently; never fixes.
- Implementer (a ringer manifest task per dispatched unit): the unit's actual work, test-first against the source plan's verbatim acceptance test.

Three validation layers stack per dispatched unit: the worker's own test-first self-check, the manifest `check` (which supplies or verifies the canonical acceptance test the worker cannot game), and the per-unit `opus` validator, with the orchestrator's gate on top of all three (full `tests/run.sh` on the integration branch).
Orchestrator-lane tasks get two layers, not three: the task's own executed acceptance check from the source plan, run by the orchestrator, plus the gate's full-suite run; their human checkpoints are the third layer.

## 4. Hazard mitigations (deviations from the source plan marked)

**Check custody (P14, and the METR reward-hacking result).**
The source plan is test-first: each dispatched task writes its own `Test:` file as part of its deliverable, and that file is the spec's teeth.
Custody is preserved without taking that away, by transport:

- T1, T2, T3 create a brand new test file. The manifest `check` writes the canonical test text (verbatim from the source plan's Step 1 block) over whatever the worker produced, then runs it. The worker still writes the test first, as the plan asks, but the text that judges it comes from the manifest, which no worker can reach.
- T4, T5, T9 extend an existing test file, so a whole-file overwrite would need the final file text to exist somewhere first. Instead the `check` asserts, by verbatim substring, that every required `fail "<message>"` assertion from the source plan's replacement or append block is present in the worker's test file, then runs the suite. A worker that deletes or weakens an assertion loses its message and fails the check with the exact missing line printed.
- In both shapes the validator additionally audits the test-file diff line by line: every deleted assertion must be one the source plan's Step 1 or Step 2 explicitly authorizes replacing, and any other deletion is a fail.

DEVIATION from the skill's blanket rule that no unit lists a check file among its owned files: here the tests ARE the deliverable spec teeth and the source plan orders them written first, so the test files stay in the ownership lists and custody is enforced by canonical overwrite (T1, T2, T3) or canonical assertion presence (T4, T5, T9) instead.

**Ringer deliverable loss (from `references/ringer-substrate.md`).**
Run-level `worktrees: true` deletes a passing task's worktree and its commits with it.
Every task therefore leaves its work uncommitted and its `check` exports the staged diff as its last act to `/Users/jjrdar/.ringer/work/i52-seam1-recording-convention/patches/<key>.patch`, outside the worktree; the orchestrator applies that patch on the integration branch at the gate and makes the commit itself, with the source plan's commit message for that task.
`expect_files` names that absolute patch path, never a worktree-relative one.
No gitignored build outputs are produced by these shell units, so no extra `cp` is needed.
The engine is `claude-zai`, not `opencode`, so the sqlite-stagger footgun does not apply; wave 1 runs `max_parallel: 3` and the single-unit waves run `max_parallel: 1`.

**Carried forward from the previous I52 run's MODEL-NOTES (real, recorded, not hypothetical).**
A `claude-zai` engine-level ERROR can end a task silently and leave its worktree taskdir behind, which makes the relaunch fail at setup; before relaunching a task that errored at the engine level, run `git worktree remove --force <taskdir>` first.
`./ringer.py lint` will report `instructs_git_commit` for T3, because Task 3's verbatim acceptance test builds its fixture with `git commit -qm "seed"` inside a heredoc.
That is a known false positive on embedded fixture text, was attributed the same way in the previous run, and is not a reason to alter the verbatim test; every real `Step N: Commit` instruction is stripped from the specs at assembly time (Section 8), so no spec actually tells a worker to commit.

**Commit steps stripped from worker specs.**
DEVIATION from the source plan: each task's final `- [ ] Step N: Commit - git add ...; git commit -m "..."` bullet is removed when the spec is assembled, because the worker never commits under the patch-export pattern.
The commit messages survive unchanged; the orchestrator runs them at the gate (Section 6 lists them).

**Scoped in-task regression gates (carried from the source plan, deliberately).**
Each dispatched task's `check` runs only the suites that task can affect, exactly as the source plan's steps specify, so a parallel neighbour's in-flight changes never fail a task on damage it did not cause.
The full `tests/run.sh` runs once per wave, at the gate, on the integration branch after every patch is applied, and again inside T10 Step 1.

**Disjoint files within every wave.**
Wave 1's three units own non-overlapping paths (T1: `scripts/session-card.sh`, `tests/sessions/session-card.sh`, `tests/hardcodes/sweep.sh`; T2: `scripts/handoff-log.sh`, `scripts/lifecycle-lint.sh`, `config/repo-state.md`, `tests/sessions/handoff-lifecycle.sh`; T4: `scripts/board-cards.sh`, `scripts/board-render-obsidian.sh`, `tests/board/cards.sh`, `tests/board/render.sh`).
