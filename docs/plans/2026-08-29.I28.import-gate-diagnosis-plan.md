# Import-gate diagnosis Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its
> acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Record a verdict on whether loop-setup's import workflow can file a tracker issue without a human genuinely approving it, on each import path, backed by a contract-and-code read.

**Approach:** Read the enforcement on both import paths - the agent path (a prose disclosure in import-triage.md, then `scripts/tracker.sh create` reached directly) and the bash `reconcile_import` fallback - and re-derive each finding with an executed check.
Consolidate the two findings into one verdict memo that answers "can creation occur unapproved, and on which path", classifies the 2026-08-23 report, and lists the three dispositions with a recommendation.
No gate or mechanism is built this pass; the deliverable is the recorded verdict.

**Tech stack:** Bash (POSIX sh / bash 3.2-compatible), grep/sed/awk, the repo's existing test scripts. No new dependencies.

**Source brief:** `docs/briefs/2026-08-29.I28.import-gate-diagnosis-brief.md`

## Global constraints

- Deliverable is a recorded verdict, not a mechanism; building any gate is out of scope this pass.
- Every path verdict cites `file:line` evidence.
- The diagnosis targets the agent import path (import-triage.md prose then `tracker.sh create`), keeping it separate from the bash `reconcile_import` fallback; the two harm models are never merged.
- The verdict memo lands at `docs/memos/2026-08-29-import-gate-diagnosis.md` (memos are not a tokened lane, per `config/conventions.md`, so hyphen grammar, no `.I28` token).
- Reproducing beyond the observed github-mode case, and fixing `is_candidate` keyword quirks, are out of scope.

## Open questions - resolved for planning

- Disposition on the verdict (close #28 / keep parked with the diagnosis attached / build a create-time gate): this is the diagnosis output, not a planning input, so it is not pre-chosen. The plan produces the verdict plus a recommended disposition - keep #28 parked with the diagnosis attached, because the agent-path exposure is confirmed and unmitigated while building is out of scope this pass - and routes the final pick to a human checkpoint. Any tracker mutation on #28 is the user's trigger.
- Gate scope (remote-only vs all modes), if a gate is built: moot this pass; deferred to a follow-up design.
- `/dev/tty` gate vs cooperative-strengthen fork: moot this pass. Recorded lean for the follow-up is the cooperative-strengthen fork, because a `/dev/tty` gate fails closed under an agent-driven Bash run (no openable controlling terminal) and would block agent-driven import creation entirely.

## Dependency graph

Linear chain; all three tasks write the single verdict memo, so ownership is sequential.

```
Task 1 (agent-path evidence + memo section) --> Task 2 (bash-path evidence + memo section) --> Task 3 (verdict + disposition)
```

Task 1's grep check and Task 2's test run are independent reads of disjoint source files, but they share the memo file, so they are sequenced, not parallel. After Task 3, a human checkpoint confirms the judgment call.

## Human checkpoints

- **After Task 3 - classify the 2026-08-23 report (brief SC3, `[judgment]`).** Confirm the memo's classification of the 2026-08-23 report as genuine-skip / by-design-reoffer / indeterminate, and which path it would have used. The plan proposes "indeterminate, most likely a genuine skip on the agent path" (the agent path matches #28's "gates `tracker.sh create`" wording and lacks a code backstop); the original session is unrecoverable, so this rests partly on inference and is the human's to confirm.
- **After Task 3 - pick the disposition, and fire any tracker mutation.** Choose close #28 / keep parked with the diagnosis attached (recommended) / commission a follow-up gate design. If the pick closes or comments on #28 on the live tracker, that outbound mutation is the user's trigger, staged for them, not run by the executor.
