# jrit-loop Plugin Port Implementation Plan

> For executors: tasks use checkbox syntax; execute in dependency order; a task is done when its
> acceptance check passes. No specific tooling, harness, or skills are assumed.

**Goal:** Ship the loop-stack toolkit as `jrit-loop`, a Claude Code plugin of eleven self-contained prose skills plus one sanctioned receipt helper, installable from a self-hosted marketplace and from the npx skills installer, with per-repo footprint reduced to pointer docs plus one managed instructions section.

**Approach:** Build a fresh product repo at `~/repos/jrit/jrit-loop` in the mattpocock/skills shape - plugin and marketplace manifests, eleven skills whose every reference resolves inside its own skill directory, one shipped executable, and repo-side CI that holds the structural gains on every push.
The eleven skills port 1:1 as prose; the shell layer dies except for the four tracker enforcement verbs an agent cannot be trusted to replicate, which ship as one helper inside the loop-drive skill.
Cutover is lazy: each rolled repo migrates when a ported skill detects its pre-plugin layout and refuses to proceed silently.

**Tech stack:** POSIX-ish bash, `git`, `gh`, `glab`, `jq`, `claude` CLI (plugin validate, plugin eval), GitHub Actions, npx `skills` installer.

**Source brief:** `docs/briefs/2026-09-12.B32.jrit-loop-plugin-port-brief.md`

### D4. Local tracker mode grammar

One file, at the path `local-issues-file:` declares (default `docs/issues.md`).

```markdown
# Issues

<!-- next-number: 4 -->

## #1 Short title, no trailing period
state: open
labels: idea, agent:todo

Body prose for issue 1.

> receipt 2026-09-13T14:02:11Z: AGENT STATUS branch=x worktree=y verdict=pass repairs=0

## #2 Another title
state: closed
labels: agent:done

Body prose for issue 2.
```

Rules, exactly:
Sections appear in ascending number order.
`state:` and `labels:` are the first two lines after the heading, in that order, each on its own line.
`state:` is `open` or `closed`.
`labels:` is a comma-plus-space list, possibly empty, and `agent:` states are ordinary members of it.
Issue numbers are monotonically increasing and assigned at create from the `<!-- next-number: N -->` marker, which is bumped in the same write.
Comments and receipts append to the body as `> receipt <UTC ISO-8601>: <text>` lines.
The receipt helper does not run in local mode; the pointer doc discloses that claim and done enforcement are absent there.

### D6. Portability-doctrine home, and the stub wording template

Deviation from the brief, recorded.
The brief puts the shared probe/use/degrade/disclose wording template in "the portability-doctrine reference".
Three skills consume the template (loop-drive for ringer and herdr, loop-plan and loop-brainstorm for rubix-review), so a shared reference file would mean three copies of a four-sentence paragraph plus two more byte-equality pairs in CI.
Instead: the template is fixed here, each consuming skill inlines its own filled-in instance, and `ci/structure-check.sh` asserts the four literal markers appear in each consuming skill.
The authoring-side portability doctrine itself is prose for contributors, not runtime behaviour, so it lives in `README.md`.

Template, with the four markers CI greps for in bold:

```markdown
**Probe.** <the exact one-line probe command or prose test>
**Present:** <what presence unlocks, in one sentence>
**Absent:** <the native fallback, in one sentence>
**Disclose:** <the exact one-line disclosure to emit when the fallback is taken>
```

Filled instances, exact:

ringer, in `loop-drive/SKILL.md`:

```markdown
**Probe.** Run `[ -f "${RINGER_ROOT:-$HOME/repos/ringer}/ringer.py" ]`; the `RINGER_ROOT` environment variable overrides the default location.
**Present:** ringer is available as a worker transport, and its scoreboard is the top evidence tier of the routing chain.
**Absent:** every unit takes the harness's own background-agent transport, and routing skips the top evidence tier entirely, falling back to benchmark prior then orchestrator pin.
**Disclose:** say in one line, in the emitted plan's pre-flight, "ringer not found at the probed path; running degraded: background-agent transport only, routing by prior."
```

herdr, in `loop-drive/SKILL.md`:

```markdown
**Probe.** Run `[ -n "$HERDR_ENV" ] && command -v herdr >/dev/null 2>&1`; when it succeeds, check compatibility at probe time with `herdr api schema --json` and never against a pinned version number.
**Present:** workers may be dispatched into herdr panes via `herdr api` instead of background agents.
**Absent:** workers dispatch through the harness's own background-agent transport, unchanged.
**Disclose:** say in one line "herdr not detected; dispatching workers through the harness's own background-agent transport."
```

rubix-review, in `loop-plan/SKILL.md` and `loop-brainstorm/SKILL.md`:

### D8. The receipt helper and its line budget

The helper is `skills/loop-drive/scripts/receipt.sh`.
loop-drive's prose refers to it as `scripts/receipt.sh` resolved relative to the loop-drive skill's own directory, and says so in those words; `${CLAUDE_PLUGIN_ROOT}` appears nowhere.
The invocation form is fixed as `bash scripts/receipt.sh <verb> ...` everywhere the helper is called, in prose, in tests, and in the decommission doc, so the execute bit is never load-bearing and an installer that drops it cannot break the helper.
`chmod +x` on the helper remains only as the marker `ci/budget-check.sh` uses to assert it is the single executable under `skills/`.

Four verbs, and nothing else:

| Verb | Signature | Behaviour that cannot be delegated to prose |
| --- | --- | --- |
| `done` | `done <num> --receipt <text> [--ran <cmd>]` | Re-executes `<cmd>` itself, captures the real exit code, posts the receipt including a failure, and on non-zero sets `agent:review` and exits 7 instead of closing |
| `claim` | `claim <num> <session-id> [--reclaim]` | Posts the claim receipt BEFORE flipping the label, then recomputes ownership over all receipts and exits 4 on a lost race |
| `status` | `status <num> <todo\|working\|needs-input\|review>` | Removes every other `agent:` status then adds one, so exactly one is active |
| `next-eligible` | `next-eligible [<session-id>]` | Stale-claim wall-clock sweep plus line-anchored `Blocked by: #N` resolution against one consistent list snapshot |

Everything else the old `scripts/tracker.sh` did (create, comment, close, reopen, label, mode, list, children, host, group) becomes direct `gh`/`glab` prose in the skills.
The helper does not support local tracker mode.

**The budget, amended, and its denominator corrected.**
Criterion 4 said "the shipped install path outside markdown stays under 150 lines", while the brief's Approach section sized the helper at "~180 lines"; the two numbers conflicted.
A function-by-function count of the ported helper with both line-savers applied estimated roughly 177 non-blank non-comment lines.
Jeremy resolved the conflict on 2026-09-13: the overrun is accepted because the function-by-function approach buys needed clarity, and the budget is amended to **under 200**.
Criterion 4 is read with that amended number everywhere in this plan.

The denominator is the helper alone, not four files.
The 200 Jeremy approved was measured against `skills/loop-drive/scripts/receipt.sh` and nothing else, but an earlier draft of the check summed four files, adding roughly 25 lines of manifest and agent-yaml overhead that the approved number never contemplated; on that arithmetic a 177-line helper fails a 200-line budget it actually fits inside.

Resolution baked into this plan:
`ci/budget-check.sh` measures the non-blank non-comment line count of `skills/loop-drive/scripts/receipt.sh` ALONE and fails at `200` or more.
It separately asserts that `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, and `skills/handoff/agents/openai.yaml` exist, and prints each one's SLOC as information only, with no threshold attached; those three are declarative manifests, not install-path logic, and their size is a fact worth seeing rather than a budget worth policing.
`LICENSE` is verbatim legal text rather than install-path logic and is excluded likewise; criterion 7 asserts its existence separately.
Two line-savers stay mandatory in Task 4 because they are simplifications on their own merits, not padding trims: issue listing uses `gh issue list --json ... -q '<jq filter>'` and `glab issue list --output json | jq`, replacing the source script's forty-line no-jq awk brace scanner, with `jq` declared a hard dependency for gitlab mode and probed at startup; and every `local)` branch is dropped.

**The escape hatch, kept for the new number.**
The 177-line figure is an estimate, not a measurement, and Task 4 measures it.
If `ci/budget-check.sh` reports a helper SLOC of 200 or more, Task 4's acceptance check FAILS and the plan does not proceed past it.
The escalation is human checkpoint C5, where Jeremy picks one of three named options: raise the budget again to a stated number; ship `gh`-only in v1 and add `glab` behind the same four verbs later, which removes roughly 40 lines of backend dispatch; or move `next-eligible` out of the shipped helper into `ci/` dev tooling and have loop-drive's prose select the next ticket by reading the tracker directly, which removes roughly 50 lines.
No option silently raises the budget; the 2026-09-13 raise from 150 to 200 was Jeremy's explicit call, recorded above.

### D9. Criterion 7's drift check

Criterion 7 says a drift check must fail "when the plugin manifest version and the package version diverge".
Decision 4 settled that `plugin.json`'s `version` is the single source, with no changesets, so jrit-loop ships no `package.json` and therefore has no package version.
Verified 2026-09-13: a `plugins[]` entry in `marketplace.json` accepts no `version` key and `--strict` rejects unrecognized keys, so the marketplace entry cannot carry a second copy either.

Resolution: the second copy is a version marker in `README.md`, which is the surface that tells a stranger what they are installing and therefore the copy that actually drifts.
