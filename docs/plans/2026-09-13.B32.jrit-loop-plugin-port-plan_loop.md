## 3. Orchestration shape and the three validation layers

Layer 1, implementer self-check: every task in the source plan already carries one `[executed-check]` acceptance command, and every task's step list starts by running that command and confirming it FAILS before the work begins.
Layer 2, per-unit validator: a fresh Opus Agent-tool subagent that re-runs the acceptance check itself, walks the criteria one by one against the artifacts, audits the diff against the ownership list, and returns a structured verdict. It never fixes anything.
Layer 3, orchestrator gate: the run JSON, the raw worker logs, the exported patches, a spot-check of one passing artifact, the union-merge of the shared allow-list, and a full `bash ci/run-all.sh` on main before the wave advances.

## 4. Hazard mitigations

**Check custody, the general rule.**
No unit may own or edit a file that its own acceptance check consists of.
Task 3 creating the `ci/` checks that gate Tasks 4 through 8 is good custody by construction and needs nothing added.

**Check custody, the two exceptions and how they are handled.**
U04 owns `tests/receipt-gates.sh` and is judged by it, and U08 owns `tests/local-mode-grammar.sh` and is judged by it.
A worker that can write its own success criterion can pass by gaming it, so both units get a three-part mitigation, and it is stated in their specs so the worker knows the audit is coming.
First, the manifest `check` for those units is authored by the orchestrator and is not merely "run the worker's test": it runs the worker's test AND asserts structurally that the test still contains every gate the source plan specifies, by literal marker (for U04: Gate 0 through Gate 6, the exit codes 4, 5 and 7, the `RACE:` string, the `skip: gitlab gates (GITLAB_TEST_PROJECT unset)` line, and the absence of `|| true` on any assertion line).
Second, the Opus validator re-runs the test itself against a fresh scratch repo and then audits the test file criterion by criterion against source-plan lines 762-774 (U04) and line 930 (U08), reporting any weakened, deleted, or vacuous assertion as a fail.
Third, the orchestrator diff-reads both test files in full at the gate; they are short and they are the attack surface.

**Check satisfiability defect in `ci/budget-check.sh` (blocks U03, then U04).**
Source-plan line 719 has `ci/budget-check.sh` assert that `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, and `skills/handoff/agents/openai.yaml` all exist.
`skills/handoff/agents/openai.yaml` is created by Task 7, so the assertion is unsatisfiable inside U03's own boundary (U03's acceptance check is `bash ci/run-all.sh`, which runs budget-check when `skills/` holds only `.gitkeep`) and unsatisfiable inside U04's boundary (U04's acceptance check runs budget-check in a worktree where Task 7 has not landed, and U04 and U07 are declared parallel).
This is the ringer rule that a check must be satisfiable by a worker obeying the spec, violated twice.
The proposed spec edit is one clause: the three existence assertions skip with a `skip:` line when the file does not yet exist, exactly as the helper SLOC measurement at line 717 already does, and the assertion becomes hard only once the file is present.
This edit changes a unit's produced contract and affects multiple units, so it is a STOP at pre-flight, not a BATCH take.

**Nested repo, Agent-tool units only.**
`/home/jjrdar/repos/jrit/jrit-loop` is a git repo nested under `/home/jjrdar/repos/jrit`, which is NOT a repo, which is in turn under the session's own cwd tree.
Built-in `isolation: worktree` would snapshot the wrong thing, so the two Agent-tool units create their own worktrees with explicit commands.
U01 needs no worktree at all: it writes one file to `/home/jjrdar/repos/jrit/`, which is not under version control, and U02 later moves that file into the repo.
U10 creates its worktree itself, with these exact commands in its brief:

**Per-worktree environments: none needed.**
The whole run is `bash`, `git`, `gh`, `glab`, `jq`, `npx`, and the `claude` CLI, all on PATH at host level with no in-project virtualenv and no install step.
No template carries an install line, and a template that grows one is a defect.

**Shared append-only file across the wave-3 parallel set.**
`ci/reference-allowlist.txt` is written by U04, U05, U06, U07 and U08, and by U09 in wave 4, one line per addition with a trailing `# why` justification, never a rewrite and never a deletion of another unit's line.
Because all five wave-3 worktrees branch from the same base and all five append at end of file, their exported patches WILL collide on that file at the gate, and that specific collision is expected, not a scope violation.
The gate resolves it by union-append in unit order (U04, U05, U06, U07, U08), then re-runs `bash ci/structure-check.sh` on main to confirm the merged list is still correct.
A merge conflict in any OTHER file is a scope violation and is handled as one; it is never quietly resolved.

**Per-unit logs instead of a shared run log (deviation from the source plan, noted once).**
No shared append-only log file exists.
Each unit writes `/home/jjrdar/repos/loop-stack-session/docs/drive-logs/B32/unit-NN.md`, and the orchestrator writes the combined wave summary at the gate.

**Drive logs live in loop-stack-session, not in jrit-loop and not in `~/repos/jrit` (deviation, noted once).**

**Ringer footguns carried from the substrate reference.**
