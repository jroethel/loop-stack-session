## 3. Orchestration shape and the three validation layers

Three tiers, transport-independent:

- Orchestrator (this session, on Jeremy's Mac): runs the wave loop, the gates, the merges, spec edits, and escalation; reads logs, verdicts, and core diffs only; never implements.
- Validator (a fresh `opus` subagent per unit): adversarial re-check of the implementer's claim against the actual artifacts (the diff, the executed check output, the produced files); never fixes.
- Implementer (a worker per unit): the unit's actual work, test-first against its acceptance check.

Three validation layers stack per unit: the implementer's own test-first self-check, the per-unit validator's independent re-check, and the orchestrator's gate (which reruns the full suite on the integration branch).

Topology:


## 4. Hazard mitigations (deviations from the source plan marked)

Check custody (both transports).
The acceptance test is the attack surface, so no worker owns its own check.
For the three ringer units the canonical acceptance test lives inline in the manifest `check` field (unreachable by the worker); the check overwrites any worker-written copy of the test with that canonical text before running it, so a worker cannot pass by editing the test.
DEVIATION: the source plan has each task write its own failing test in Step 1; here the worker writes only the implementation script, and the harness supplies the canonical test.
The worker's ownership list names only its one implementation script; a worker diff that touches any other file is an automatic scope violation the validator fails, not a gate negotiation.

Ringer deliverable loss (from `references/ringer-substrate.md`).
A passing ringer worktree is deleted and its commits die, so each manifest `check` exports the staged diff to `/Users/jjrdar/.ringer/work/i52-obsidian-board-mvp/patches/<key>.patch` (outside the worktree) as its last act; the orchestrator applies that patch on the integration branch at the gate.
No gitignored build outputs are produced by these shell units, so no extra `cp` is needed.
`max_parallel` is 1 and each wave packs a single ringer task, so the opencode sqlite-stagger footgun does not apply (the engine is `claude-zai`, not opencode).

Linked-worktree substrate (nested/linked-repo hazard).
The execution repo `/Users/jjrdar/create/loops/loop-stack-session-i52` is a LINKED git worktree of `/Users/jjrdar/create/loops/loop-stack-session`, and the ringer manifests set `repo` to that linked worktree with `worktrees: true`.
DEVIATION from the toy assumption: pre-flight proves `git -C /Users/jjrdar/create/loops/loop-stack-session-i52 worktree add` succeeds off the linked worktree before wave 1 (a linked worktree registers new worktrees at the shared common git dir; confirm, do not assume).
If `git worktree add` fails off the linked worktree, STOP and ask the human rather than falling back silently.

Agent-tool units run in place (no `isolation: worktree`).
DEVIATION: the harness default gives each subagent its own worktree; T1 and T5 instead run in the live i52 worktree on branch `i52-obsidian-board-mvp`, because they need the real Mac's Obsidian runtime, real `gh` auth, and the live Cortex vault, which a repo-only worktree copy does not provide.
Their repo-file writes are disjoint from the concurrent ringer worktrees (T1 owns `assets/board/*`, `docs/spikes/*`, `tests/board/spike-artifacts.sh`; T5 owns `tests/board/integration.md`), so nothing collides.
Because they are in place there is no branch to merge: T1 leaves its artifacts committed once its own spike test passes, and the gate reviews that commit.

Shared append-only files.
There are none in this build; per-unit logs are the tickets' `AGENT STATUS` receipts on issue 52 plus the ringer worker logs under `<workdir>/logs/`, and the orchestrator writes the combined wave summary into the batch-review journal.

Disjoint-files assumption.
Within each wave the units touch disjoint files by construction (wave 1's T1 and T2 own non-overlapping paths; waves 2-4 have one unit each), so a conflict when applying a wave's patch is a scope violation, not something to quietly resolve.

Outward-facing writes are bounded by the brief.
The only sanctioned writes outside the repo are, in the Cortex vault, `<CORTEX>/00_System/Board` (the board home), the T1 spike scratch dir `<CORTEX>/00_System/_board-spike/` (created and deleted by T1), and optionally `<CORTEX>/.obsidian/snippets/loop-board.css` (written once by T4/T5 only when the spike recorded CSS-needed: yes).
Any write beyond those is an outward-facing STOP that asks the human.

## 6. Wave loop and gate procedure

Run waves 1 through 4 in order.
Gate-class tags (STOP, BATCH, DEFAULT) follow the loop-auto skill; under `auto` the DEFAULT and BATCH takes fire without asking, STOP always asks.

For each wave:

1. Launch.
   Ringer units: `cd /Users/jjrdar/repos/ringer && ./ringer.py lint <wave-N.json> && ./ringer.py run <wave-N.json>` with the SAME `run_name` (`i52-obsidian-board-mvp`) every wave; ringer's built-in single retry IS the repair pass, add none.
   Agent-tool units (T1 in wave 1, T5 in wave 4): launch as a background subagent with the Section 8 brief; on completion launch its validator; on a failed validation send one repair pass to the same implementer with the itemized verdict, then revalidate; a second failure stops that unit without blocking siblings.
   On claiming each unit, write the receipt: `scripts/tracker.sh comment 52 "AGENT STATUS branch=i52-obsidian-board-mvp worktree=<path> verdict=working repairs=0 wave=<N> unit=<key>"`.

2. Gate (orchestrator).
   Ringer: read the run JSON in `~/.ringer/runs/` (the run JSON is truth, not a detached shell's exit status); read every retried or failed worker log in `/Users/jjrdar/.ringer/work/i52-obsidian-board-mvp/logs/`; spot-check at least one passing artifact.
   On a ringer FAIL, attribute before relaunching: rerun the canonical check's steps yourself against the tree; if the worker's output was correct and the CHECK was wrong, fix the check in the manifest, commit the audited work, and annotate MODEL-NOTES instead of burning a round.
   Apply the exported patch to the integration branch: `git -C /Users/jjrdar/create/loops/loop-stack-session-i52 apply --index /Users/jjrdar/.ringer/work/i52-obsidian-board-mvp/patches/<key>.patch` then commit with the source plan's message for that task.
   Agent-tool: review the committed diff (T1) or the recorded runbook plus a fresh `tests/run.sh` (T5); a scope-boundary violation in the diff is a fail.
   Run the full suite on the integration branch: `bash /Users/jjrdar/create/loops/loop-stack-session-i52/tests/run.sh`; advance only when green.
   Update the receipt: `scripts/tracker.sh comment 52 "AGENT STATUS branch=i52-obsidian-board-mvp worktree=<path> verdict=<pass|fail> repairs=<n> wave=<N> unit=<key>"`.
   Write the wave summary and the gate decision into `docs/reviews/2026-09-02.I52.obsidian-board-mvp-batch-review.md`; prune any native worktrees (ringer prunes its own).

3. Distill before advancing.
   Turn any repeated failure pattern from this wave's verdicts into a fix in the affected manifest spec or the T1/T5 brief before the next wave.
   Leave the dated MODEL-NOTES receipts in `/Users/jjrdar/repos/ringer/docs/MODEL-NOTES.md`: one line per (model, task_type) per wave (`glm-5.2`/`code-feature` for the ringer waves; `opus`/`site-build` for wave 1's T1, `opus`/`probe` for wave 4's T5), plus a separate line for any signal event (a pin, a runtime re-route, a check-bug attribution, an off-nominal result), supported only by validator verdicts and diffs.

4. Advance only on a green integration branch.
